An institutional AI workflow is not priced meaningfully by counting prompts alone. The cost depends on the work product, the systems it reads, the volume and variability of inputs, the controls it must preserve and who operates it after launch. A useful scoping conversation makes those responsibilities visible before comparing proposals.

This unreleased draft awaits procurement and editorial review. It contains no quoted prices, customer savings, market price ranges or promises about an available integration.

## Separate setup from recurring operation

Setup can include source mapping, permission design, evaluation cases, calculation rules, artifact templates and reviewer acceptance. Recurring operation can include run volume, monitoring, exception handling, source changes, model changes and support. A proposal that combines these into one number may be legitimate, but the buyer should still understand what is included.

The firm's own effort also matters. Data preparation, access approvals, reviewer time and correction work do not disappear because they are absent from a vendor invoice. Measure them separately so that one offer does not appear cheaper by moving work onto an internal team.

## Cost-driver register

| Driver                 | Information to collect                               | Why it changes scope                                  |
| ---------------------- | ---------------------------------------------------- | ----------------------------------------------------- |
| Work product           | Required fields, format and release standard         | A draft summary differs from a reconciled review pack |
| Source systems         | Owners, permissions, interfaces and export formats   | Each boundary needs mapping and testing               |
| Input variability      | Document types, scan quality and exception classes   | Unpredictable inputs require more handling            |
| Volume and peaks       | Attempted cases and reporting deadlines              | Peak load can dominate operating design               |
| Control requirements   | Fund/investor scope, audit record and approval rules | Controls add implementation and verification work     |
| Permitted actions      | Read-only, draft creation or narrow writes           | Writes require stronger reconciliation and recovery   |
| Service responsibility | Monitoring, support and change ownership             | Software access differs from an operated workflow     |
| Exit requirements      | Export, credential revocation and retention          | A usable handover must be designed                    |

Unknown inputs should produce a discovery task or a stated assumption, not an unsupported fixed estimate. Ask which assumptions would trigger a change in scope.

## A cost model without invented prices

Define monthly operating cost as the sum of provider charges, infrastructure charges, internal review effort, correction effort and allocated operating support. Keep one-time setup separate and decide explicitly whether to amortize it for comparison. Do not count the same support work in both a provider fee and internal labor.

Cost per accepted artifact equals the agreed total cost for the period divided by accepted artifacts in that period. If no artifact is accepted, the ratio is undefined, not zero. Also report cost per attempted case so that a low acceptance rate remains visible.

Compare like-for-like artifacts and source conditions. A cheap draft that requires extensive reconstruction is not equivalent to a source-attached package accepted under the firm's review rules. Conversely, an elaborate control set may be unnecessary for a low-consequence internal draft; scope controls to the actual risk without weakening required boundaries.

## Synthetic sensitivity example

Suppose a fictional workflow attempts 100 cases in a month. At 10 reviewer minutes per attempt, review consumes 1,000 minutes. At 15 minutes per attempt, it consumes 1,500 minutes, an increase of 500 minutes, or 8 hours and 20 minutes. No labor rate is assumed, so this is an effort calculation, not a dollar saving or quote.

If only 80 cases are accepted, the review burden is 12.5 minutes per accepted artifact in the first scenario and 18.75 in the second. That comparison still excludes setup, correction and operating support. The point is to identify which assumptions deserve measurement, not to manufacture a return-on-investment claim.

## Questions that make proposals comparable

Ask what constitutes a billable attempt, whether retries are charged, how failed source retrieval is handled and what usage limits apply. Clarify peak-period support, incident response, source-system changes and evaluation after a model change. Record exclusions in ordinary language.

For a managed engagement, ask who owns unresolved exceptions and who can approve changes. For a software-only offer, identify which responsibilities remain with the firm. Neither model is automatically superior; a comparison must include the work the buyer will actually perform.

## Decide with evidence, not a generic range

Start with a bounded pilot and measure accepted outputs, reviewer minutes and exception classes. Use the observed scope to refine the operating estimate. Do not extrapolate from one clean demo to an entire portfolio without testing source and control differences.

## Sources and limitations

This is a proposed commercial scoping framework, not a price list, offer, valuation or financial forecast. The volume and effort example is synthetic and independently reproducible. Real estimates require confirmed source access, scope, reviewer obligations and commercial terms. No customer economics or vendor pricing evidence was supplied for this draft.
